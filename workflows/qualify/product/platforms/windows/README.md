# Windows product qualification

The Windows lane requires an explicitly selected Windows installation and an
absolute path to the candidate Dockpipe executable. A paired remote Windows
target can qualify product features. Host VM installation, start, embedding,
shutdown, and disk-only restart require separate evidence from the normal GUI.

Invoke `driver.py --request ABSOLUTE_REQUEST_JSON --output ABSOLUTE_NEW_DIRECTORY`
using Python 3 inside Windows. Its strict configuration contains `cli` (absolute
installed executable), `cli_sha256`, `artifact` (absolute selected MSI or ZIP),
and optional `timeout_seconds` (5–180, default 60). The driver checks that the
native Windows architecture and executable PE architecture match the selected
platform profile before starting the CLI. The artifact and executable must
match their SHA-256 pins.

An MSI also requires `install_receipt`, the absolute path to the successful
installation receipt produced by `prepare-product.ps1`. Keep the installer log
beside the receipt. The driver checks that the receipt links this request,
installer, and installed executable, verifies the log digest, and retains
both files as evidence. For a portable ZIP, the driver verifies that the
selected executable matches the archive's root `dockpipe.exe`. The
`windows-amd64-msi` profile requires the MSI path.

The `install.cli` happy case at `installed_e2e` runs native identity/version
admission, public `dockpipe init` in a new private workspace, and a public host
workflow that writes and prints an exact fixture marker through PowerShell.
It requires `installed-cli-version`, `initialized-project`, and
`host-workflow-executed` together. Logs and bounded command receipts remain in
the output with evidence hashes. Other cases stay blocked until implemented;
running this adapter on another OS cannot pass Windows cases.

Run the identity admission probe inside the selected Windows environment:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File inventory.ps1 -Dockpipe C:\candidate\dockpipe.exe -Output C:\evidence\identity-01
```

The output directory must be new. The probe records the actual Windows version,
build, architecture, CPU and memory inventory, and the candidate executable hash
and version. This evidence admits the target; it does not mark product feature
cases passed. Run feature cases only after the shared qualification request has
selected them and preserve each command's bounded result and evidence hashes.

For a fresh VM, select a new disk and isolated workspace/profile. Installation
must preserve that new guest's identity, firmware variables and TPM state for
later starts. Do not adopt an existing image whose firmware/TPM authority is
ambiguous. Credentials generated by an owning provision workflow stay private
in the new guest's state and are excluded from public receipts and source.

Guest provisioning is serialized with other guest lanes and subject to the
operator's resource admission. Firmware-only display, mocked native display
tests, and a visible installer are distinct from an installed Windows desktop
and from Windows product feature acceptance.

`payload.py` stages the pinned MSI, official embeddable Python runtime, and native
test scripts through the owning VM workflow's Bootstrap Media Path input. It
does not generate or replace Windows provisioning, credentials, TPM, firmware,
or unattended installation assets. `prepare-product.ps1` installs only into an
explicitly selected fresh guest, refuses existing product state, verifies the
default MSI CLI/GUI/Qt/shortcut payload, and invokes the native CLI driver.
It records the installed GUI hash without claiming a rendered GUI observation.

`observe-gui.ps1 -FreshGuestDesktop` uses an existing interactive fixture login through a temporary
user task, launches the pinned installed GUI, and records its actual window and
fresh guest desktop screenshot. It requires no account password or new login.
The exact temporary task is removed. Its execution limit is two minutes;
further UI tests must observe the recorded GUI process's liveness rather than
assuming it remains available. Process-scoped script execution flags do not alter machine
execution policy. The observation does not qualify embedded input or feature
behavior. A missing interactive login remains a prerequisite failure.

`lifecycle.py` reuses the owned desktop and AT-SPI helpers from the Linux lane.
It supplies the Windows profile, bounds resources, refuses an existing install
disk, opens the normal VM workflow form, and reads back configured media and
hardware fields. Actual Launch additionally requires an explicit serialized
guest slot grant. Disk-only restart requires an explicit captured identity and
observed installation, the same workspace and durable state directory, unchanged
disk/firmware/TPM identities and UUID, the same QEMU artifact, and absence of the
previous exact guest processes. A fresh owned GUI process uses `provided-only`
and omits installer, driver, unattended floppy and bootstrap media overlays;
the normal form must also clear saved media. Verify actual QEMU arguments after
launch independently before accepting the restart. Public guest shutdown requires
the exact owned run ID in its fresh provisioned resource title and reads back
selection before requesting shutdown. Stopped-state observation is separate;
resource titles may change when Guest Tools stop, and ambiguity must remain
unresolved until an exact package resource snapshot can identify the run.
Closing the test GUI is not guest cleanup. Host GUI field automation and native
Windows scripts require live qualification after a slot grant.

For an installed guest that needs setup before SSH works, select the owning
package's **Manual setup** choice on Advanced. It skips the SSH-backed guest
command and startup wait; it does not attest transport readiness. The controller
scrolls the normal form until the choice and its popup fit inside the visible
viewport above Launch, then clicks the declared option and reads it back. It
never uses Return as a dropdown fallback because that can accept Launch.

The host artifact inventory includes the GUI executable, its shared UI library,
and terminal helper. Preserve that complete artifact set before rebuilding a
host GUI during qualification. Record any new host artifact stage explicitly,
and repeat actual disk, media, identity and transport admission before applying
an owning guest repair. Helper status alone cannot replace actual SSH and
guest-agent health observations.

`native_arguments.py` validates forwarding in an **independently admitted QEMU
argv snapshot**, element by element. Use
`lifecycle.NATIVE_ARGUMENTS.validate_forwarding(argv, expected_ssh_host_port)`
from a host observer after checking the exact QEMU process/artifact/guest identity.
This Windows qualification profile requires exactly one `user` netdev; any
additional user, socket, tap or other backend is rejected. It requires exactly
one TCP `127.0.0.1:<selected-port>-:22` SSH forward and one
TCP `127.0.0.1:<fresh-dynamic-port>-:47831` Agent forward, with distinct host ports
in 1–65535. It rejects extra/duplicate forwards, wildcard/nonloopback addresses,
unsupported protocols, guest forwarding and alternative network-option syntax.
The next `-device` argument is never part of the `-netdev` value. Do not substitute
a prior run's dynamically allocated Agent host port or join argv for matching.

The public lifecycle dependency inventory includes this parser. The public
lifecycle adapter currently has no automatic post-Launch QEMU argv collector;
exporting the validator does not add one or migrate frozen task observers.
Parsing arguments does not prove socket reachability, SSH authentication, Agent
health, native process identity, or a product feature pass. Capture those as
separate fresh observations. No historical Windows10 snapshot is changed.

python3 -m unittest discover -s workflows/qualify/product/tests -p test_windows_native_arguments.py
