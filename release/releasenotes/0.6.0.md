# Dockpipe v0.6.0

Visit [dockpipe.com](https://dockpipe.com) for the Dockpipe website.

The 0.6.x release brings Dockpipe's workflow tools together in a desktop launcher
and a standalone CLI. Run your own project commands, add reusable workflows from
the Marketplace, select secret environments and try running selected work on
another machine. You can use the installed application without a Dockpipe source
checkout or Go compiler.

## Workflow editor, execution monitoring and a refreshed desktop

### Build and run workflows visually

The Workflows page now opens a visual editor for commands, scripts, packaged
workflow calls and parallel groups. Switch to YAML for advanced settings, validate
before saving, and run through the same local or paired-machine controls. Your
workflow remains an ordinary YAML file; canvas positions are local preferences.

New projects leave vault setup opt-in, so `dockpipe init` no longer configures a
missing 1Password template. Existing secret configuration is preserved.
Workflow state also supports linked home-directory layouts such as Bazzite's.
In Flatpak, the script picker browses the workspace directly and keeps document
portal IDs out of new script commands. Re-add a script if an older draft contains
a path such as `../../<document-id>/script.sh`.

### Edit project files and review Git changes inside Dockpipe

The new **Files** page browses the selected project and creates, edits, renames and
deletes files in a built-in text editor. It includes line numbers, basic syntax
colors, find, undo and save, with unsaved-change prompts and protection against
overwriting changes made elsewhere. Text files must be UTF-8 and at most 1 MiB.

Each workflow also has its own **Files** button, scoped to the folder containing
its YAML. Editing that workflow's YAML shares the same draft as the canvas.
Save a new workflow first to establish its folder.

**Git** belongs to the project, independent of the workflow you have open. Review
changed files and diffs, select files to commit, enter a message, and push the
current branch to origin. Pull requires a clean checkout and only fast-forwards.
Save editor drafts before reviewing Git. Existing Git credentials and identity
must already be configured; this first version does not include branch management
or a merge-conflict editor.

### Organize applications in persistent spatial workspaces

The optional Cockpit now lets you create themed planets, place configurable
buildings and walk through their interiors. Arrange application displays on walls,
resize them and save the layout for your next session. Choose workspaces directly
or fly to them; the spaceship can be hidden.

Displays reference your existing applications. Connecting uses the experimental
native app HUD, and leaving a room keeps the application running. Saved layouts
never launch or capture apps automatically; missing or ambiguous applications need
your choice. The Applications catalogue and conventional desktop pages remain
available. Native app control retains its existing X11 and app-compatibility limits.

Dashboard tiling improves RustDesk discovery and rendering, fills application
tiles without shadow margins, and releases nested windows when Dockpipe closes.
The terminal remains responsive during heavy output and supports the older
WebEngine runtime shipped on Linux ARM64.

Linux x64 Cockpit packages use a pinned, attested ForgePipe SDK. Public native
artifacts exclude private debug data; required runtime exports and license
notices remain included. Cockpit's native SDK integration is currently available
on Linux x64.

### See what is running and where resources are going

Open **Executions → Processes & resources** to inspect recent Dockpipe-managed
processes, their lifecycle and available CPU/memory measurements. The **System**
view adds a searchable process list with sortable columns and overall CPU, memory,
swap, disk, network and uptime information. Sorting and selection survive refreshes.

**Runs & logs** brings local run logs and stop controls together with remote job
status, cancellation and result downloads. It replaces the separate Activity page.
Empty history explains how to start a run, and actions follow the selected run.

### Inspect containers and paired machines

The **Containers** page replaces the Docker navigation label. Its resource canvas
shows containers, networks, volumes and their relationships, with selectable
details, logs, lifecycle controls and a shell action for local running containers.
Layer filters and movable panels help keep larger views readable.

System monitoring and container inventory can switch between this computer and a
paired remote machine. Remote monitoring requires updated broker/worker binaries
and an explicit opt-in on the worker using `dockpipe remote monitoring --system
--docker`. Remote container views are read-only; remote start, stop, shell and raw
container logs are not included. `dockpipe remote monitoring --disable` turns off
sharing without removing the pairing.

### More room for your workspace

The View menu now matches the sidebar. Hide or restore the sidebar using the
spaced header control, **View → Show sidebar**, or **Ctrl+B**; the preference is
remembered. Shared icons, canvas controls and light/dark surfaces keep the editor,
container views and execution pages consistent.

### Current limits

Native system/process resource collection is available on Linux. macOS and Windows
retain supported lifecycle information but do not yet have native system metrics.
Docker inventory uses the configured Docker engine. QEMU measurements describe
its host process, not the guest OS. Discovered system processes are read-only and
are never treated as Dockpipe-owned. Local run logs cover runs started by the
current launcher session; telemetry is bounded recent history, not an audit archive.

## Independent optional package releases

DorkPipe orchestration, its MCP service and the VS Code extensions now have their
own release pipeline. Dockpipe core builds and runs without their source. The
Linux amd64 catalog pins DorkPipe 0.6.4 and Pipeon 0.6.5; other native platforms
retain their previously qualified package versions.

Pipeon development is paused, and its packages are hidden from normal discovery.
Existing explicit installations and dependency resolution still work. The CLI
catalog command accepts `--include-hidden` when you need to inspect hidden entries.
Package authors can set `hidden: true` in installable package metadata.

## Earlier maintenance updates

Flatpak terminal commands now retain the selected project folder, including mounted
drives and paths containing spaces. `dockpipe init` no longer falls back to the home
directory when the shortcut starts Flatpak. The launcher upgrades its previous
generated shortcut automatically while preserving native or user-modified commands.
An unavailable project folder fails before initialization.

Package listings now use clearer display names and descriptions, with Apps,
Workflows, Integrations and Core discovery types. Package authors can maintain
titles, descriptions and purpose categories in their source metadata; compiled
catalogs and installed-package inventory retain these fields without changing
package IDs or installation commands. Older catalogs remain supported.

Compatible workflows now declare macOS support and describe their host prerequisites.
Linux-specific workflows remain restricted. Remote-machine setup better handles
service executable updates and paired-worker status, and the Machines page avoids
an unnecessary scrollbar when its content fits.

The launcher shows package download and stored archive sizes in the Marketplace
and Installed views. Older catalogs without size information show an explicit
unavailable value instead of a misleading zero.

Remote-access setup now links directly to compatible provider packages in the
Marketplace and selects a newly installed provider when you return. Existing remote
addresses stay visible and pre-fill setup, with a review action for connections whose
provider details have not been recorded. Provider setup continues through the same
guided authentication, tunnel and connection checks used by the CLI.

Installation examples default to production. Website builds can select staging
download URLs, APT settings and Marketplace instructions explicitly, while keeping
staging-only Homebrew commands out of production pages. Maintainers can configure
an immediate Homebrew sync after successful staging publication; the tap retains
its native Mac checks and scheduled fallback before publishing package updates.

The Flatpak launcher now sets up the `dockpipe` terminal shortcut automatically
on first launch when no existing host command is found. Bash, Zsh and Fish receive
the missing PATH configuration; open a new terminal after launching Dockpipe.
Existing commands and conflicting shell configuration are preserved, with setup
failures shown in the launcher. Desktop sessions without a working tray keep the
window accessible, and a known harmless Qt Wayland warning is filtered narrowly.

Pipeon's desktop dependencies have been updated and its native clipboard bridge
is restricted to the configured local editor origin. Native builds and clipboard
access checks now run on Linux, macOS and Windows. Dependency update PRs target
`dev` for qualification before release; GitHub security updates still initially
target the repository's default branch.

Pipeon's Linux desktop shell includes a compatibility backport for the GLib
string-iterator vulnerability RUSTSEC-2024-0429, with an optimized regression test.
Cloud storage cache rules now honor publisher cache-control headers by default,
so mutable release catalogs can refresh without waiting for a forced CDN TTL.
Existing infrastructure requires applying the updated rules and purging old
mutable cache entries.

Release setup and cloud storage workflows now require your own repository, endpoint,
bucket and state settings. Personal environment identifiers and machine paths have
been replaced with placeholders. A public-content check guards source and package
archives against these configuration leaks. Official installation URLs are unchanged.

## What's new

### A desktop workspace for your workflows

The launcher brings **Apps**, **Workflows**, **Machines**, **Containers** and **Executions** into one
window. Save project contexts, choose a workflow and execution machine, start or
stop runs, and inspect progress and logs. The same workflows remain available from
the CLI for terminals, servers and CI.

Desktop installers include the launcher and matching CLI. Choose a CLI-only
installation when you do not need the desktop app.

### Install the tools you need from the Marketplace

Open **Packages → Marketplace** to browse optional workflows and tool integrations.
Inspect their platform and dependencies, then install selected packages into your
user store. Downloads are checked against the catalog checksum. The **Installed**
view shows both user-installed and installer-managed packages.

Base installations include required core. Optional packages, their external tools
and provider sign-ins are separate. Removing an optional user package preserves its
data and settings. See [using packages](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/packages/package-quickstart.md).

### Create and reuse your own workflows

Use `dockpipe init hello` to create a workflow in your project, validate its YAML
before running it, and combine host commands, container steps and packaged
workflows. Host workflows can run without Docker when container preflight is
disabled; container workflows need a reachable engine.

Workflow outputs and reusable container image artifacts help connect steps and
avoid unnecessary image rebuilds. The [first-workflow guide](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/onboarding.md)
starts with a small host command, then adds a container.

### Select a secret environment for each run

Named environments bind selected secret values to workflow environment variables.
Adapters are available for **1Password Environments**, **AWS Secrets Manager**,
**Azure Key Vault** and **Infisical**. Select a configured environment with
`--secret-environment NAME`; configuration stores references rather than secret
values. Existing 1Password vault templates remain supported.

Install and authenticate the matching provider CLI first. The 1Password adapter
requires an `op` build with `op run --environment`; AWS bindings currently require
string fields in a JSON secret. See [secret environments](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/runtime/vault.md)
for setup and provider limits.

### Remote workflow delivery — preview

Pair a worker using a verification code and explicit approval, without transferring
an invitation file or opening inbound SSH on the worker. Preview the selected
workflow sources, assets and package dependencies before submission, then inspect
job results and cancellation through the CLI or launcher.

Remote setup currently targets **Linux and macOS**. The Cloudflare Tunnel resolver
uses your own Cloudflare account and managed domain; workers connect outbound.
Use the same updated CLI on the broker and worker. Windows workers, a hosted
Dockpipe Cloud service and complete native Mac pairing/sleep-wake qualification
are not included in this release's verified remote experience. Start with
[remote setup and limits](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/runtime/remote-nodes.md).

### Reusable AI workflows and persistent package data

Optional AI packages let you choose a provider, supply repeatable inputs and inspect
outputs. DorkPipe workflows can add task orchestration, model policies and review
steps. Provider accounts, authentication and any model charges remain separate;
available approval and isolation controls depend on the selected workflow and
runtime. See [AI workflows](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/workflows/agentic-workflows.md).

Durable package settings and continuity data are separated from disposable project
builds and caches. `dockpipe clean --dry-run` previews the project files that ordinary
clean would remove; durable package state stays outside that cleanup.

## Install

Choose the release asset for your OS and CPU. Native downloads cover Linux amd64
and arm64, macOS Intel and Apple Silicon, and Windows x64. Package availability
does not imply that every distribution, provider or workflow has been qualified.

Native host steps need **Bash**; Git for Windows provides it on Windows. **Docker
is needed for container workflows**, not the host-only example below. Provider
CLIs and Git are needed by workflows that use them.

### Linux

The installer selects a native CLI package for supported package-manager families,
or a portable archive, and verifies its downloads against the release checksums:

```sh
curl -fsSL https://github.com/Dockpipe-Industries/dockpipe/releases/download/v0.6.0/install.sh -o /tmp/dockpipe-install.sh
DOCKPIPE_VERSION=0.6.0 sh /tmp/dockpipe-install.sh
export PATH="$HOME/.local/bin:$PATH"
```

For the **desktop on Ubuntu 22.04 / 24.04 or Pop!_OS 22.04**, download the matching
CLI and desktop DEBs from this release, verify them against `SHA256SUMS.txt`, then
install both:

```sh
sudo apt install ./dockpipe_0.6.0_amd64.deb ./dockpipe-desktop_0.6.0_amd64.deb
```

Use `arm64` filenames on ARM64. Open **Dockpipe** from the application menu.
RPM, APK and Arch packages are CLI-only. The same desktop DEBs are installation-tested
on Ubuntu 22.04 and 24.04; that does not establish every downstream desktop setup.

### macOS

Install the CLI for Intel or Apple Silicon:

```sh
curl -fsSL https://github.com/Dockpipe-Industries/dockpipe/releases/download/v0.6.0/install.sh -o /tmp/dockpipe-install.sh
DOCKPIPE_VERSION=0.6.0 sh /tmp/dockpipe-install.sh
export PATH="$HOME/.local/bin:$PATH"
```

Desktop artifacts are named `dockpipe-desktop_0.6.0_darwin_arm64.dmg` for Apple
Silicon and `dockpipe-desktop_0.6.0_darwin_amd64.dmg` for Intel, and require macOS 13
or newer. They contain **Install Dockpipe.pkg** for the app and CLI together.
Current desktop packaging is not Developer ID signed and notarized, so Gatekeeper
may block installation. Do not disable macOS security protections to install it.
Use one installation method; the DMG installer refuses an existing foreign CLI or app.

### Windows

Download and run the installer in PowerShell:

```powershell
$installer = Join-Path $env:TEMP 'dockpipe-install.ps1'
Invoke-WebRequest https://github.com/Dockpipe-Industries/dockpipe/releases/download/v0.6.0/install.ps1 -OutFile $installer
& $installer -Version 0.6.0 -SkipWSLSetup
```

The script verifies checksums and prefers the MSI when it is attached, with a
CLI-only ZIP fallback. The MSI includes the launcher by default; its interactive
installer lets you deselect that feature. Open a new terminal after installation.
WSL is optional and the command above skips its setup. Windows Authenticode signing
is not yet part of the release packaging.

### Staging channels and Flatpak

The [installation guide](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/install.md)
also documents the signed **staging APT repository**, **staging Homebrew formula
and cask**, and the **Linux amd64 Flatpak preview**. These are separate staging
choices; do not mix staging and production APT sources.

The Flatpak contains the launcher, CLI and core, requires KDE Platform 6.10, and
uses a matching Marketplace catalog. Get it from the staging package host using
the guide; do not assume it is attached to this GitHub release or listed on Flathub.
App updates require downloading and verifying a newer bundle. There is no ARM64
Flatpak catalog, and full Bazzite/Podman/SELinux qualification remains outstanding.

## Try your first workflow

In a folder you own, run `dockpipe init hello`, then replace
`workflows/hello/config.yml` with:

```yaml
name: hello
docker_preflight: false
steps:
  - id: greet
    kind: host
    cmd: printf 'Hello from Dockpipe!\n'
```

Validate and run it:

```sh
dockpipe --version
dockpipe workflow validate workflows/hello/config.yml
dockpipe --workflow hello --
```

This prints `Hello from Dockpipe!` and needs no container engine. For Flatpak,
replace `dockpipe` with `flatpak run --command=dockpipe com.dockpipe.Dockpipe`.

## Upgrading and known limits

- **Moving from 0.5.x:** install the matching native application and core, then
  review the [workflow guide](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/workflows/workflow-authoring.md)
  and install the optional packages your workflows use. `--workflow` selects a
  workflow; `--template` remains a compatibility alias for the low-level image
  override and is not an interchangeable workflow selector.
- **Existing package data:** keep legacy data until its migration has succeeded.
  Inspect `dockpipe clean --dry-run` before cleanup: ordinary clean removes the
  entire disposable `bin/.dockpipe/` tree. Back up project and package data before
  upgrading; do not assume everything inside an older generated directory is
  expendable.
- **Remote provider name:** new Cloudflare setup uses
  `dockpipe.cloudflare.remote-edge`. Existing `cloudflare` resolver installations
  are not renamed automatically. Install the new resolver before using new setup
  instructions.
- **Channels and dependencies:** staging installation does not change saved package
  remotes automatically. Check **Settings → Package Remotes**. Optional package
  dependencies, external tools and provider authentication are separate setup steps.
- **Isolation:** host commands execute with the permissions of their runtime.
  AI access declarations are not a complete operating-system sandbox, and an
  arbitrary command does not automatically gain a human approval gate.
- **PipeLang:** optional typed workflow configuration remains available. The broader
  language/compiler program is experimental; these notes do not promise a
  production-ready general-purpose language, self-hosting compiler or application
  generator.

See the [CLI reference](https://github.com/Dockpipe-Industries/dockpipe/blob/v0.6.0/docs/cli-reference.md)
for commands, or [report a problem](https://github.com/Dockpipe-Industries/dockpipe/issues)
with your Dockpipe version, platform and steps to reproduce it.

### A clearer built-in file and Git workspace

Project and workflow files now share a cleaner editor with custom icons, a spaced
file explorer, a focused file header, an actions menu and an on-demand search bar.
The native editor highlights code and multiline strings/comments across C, C++,
C#, Java, Go, Rust, Python, JavaScript, Ruby, PipeLang, R, shell, Kotlin and PHP,
alongside YAML, JSON and other common project files. Language, encoding and cursor
position stay visible. Editing, indentation and zoom all remain inside Dockpipe.

Git now reviews one selected file at a time with syntax/diff colors, clear change
badges and a dedicated commit panel. Checks still choose exactly which saved files
enter the commit. The editor remains lightweight: no embedded browser or language
server is required. It is a text editor with syntax highlighting, not a full IDE.

### Explore your workspace as a graph

Choose **Graph** in the Files explorer to see folders and files on an interactive
canvas. Expand just the branches you need, zoom and pan, and open files directly
in Dockpipe's built-in editor. Workflow graphs stay within the workflow's file scope.
Use the **2D / 3D** toggle to explore a spatial grid: middle-drag or Shift-drag to orbit, drag the
background to pan, and scroll to zoom. Switching back preserves your 2D arrangement.
The 3D view has a circuit-board city style: files are chips, folders are taller
blocks, and connections follow circuit traces with readable labels. File chips
grow with file size on a bounded logarithmic scale; labels show their sizes.
Selected labels stay above nearby chips and readable when zoomed out. 3D uses
hardware rendering when available, with a software fallback and an option to
disable acceleration.
The normal 3D view now has a navigation drone: click to hover, open a file to land,
or double-click a folder to fly through its hangar into the children. Parent/Root
controls return to earlier levels, and the animation can be disabled in Options.
For a bonus view, **Options → Drone flight · Easter egg** lets you fly through
cyberpunk towers and folder hangars with WASD, Q/E altitude, right-drag look and
Shift boost. Folder doors open as you approach; crossing the threshold loads that
directory as another world. Backspace returns to the parent, N loads the next
page, and Escape returns to your graph. Worlds are paged and replaced to keep
memory bounded. The simulation pauses when controls are released or focus is lost.
Aim at a file and fire with **left-click / Space** to open the same built-in editor
in a translucent cockpit HUD. Flight pauses while you edit; Ctrl+S saves, and
Escape returns to flying with your draft and undo history preserved. Existing
file-size, binary-file and disk-conflict checks still apply.

Large folders load in pages with an explicit **Load more** action. The view caps
visible nodes, releases collapsed branches, and closes its reader when you leave.
It uses the native canvas without a background indexer or physics simulation.
This first version shows filesystem relationships; code dependency overlays are
not included.

Workflow YAML opened in Files or the flight HUD now has **Open as workflow**, which
leads into Workflow Studio's existing validation and Run controls. Scripts open
for editing; shooting a file never executes it.

An optional **App billboards** experiment lets native Linux X11 users select up to
three open windows before a drone flight. Their reduced-rate live previews appear
in the city; shoot one to control the real app in a front-facing panel inside
Dockpipe. Return to flight restores it to the desktop. The experiment is off by
default, keeps capture local, and releases selected windows when flight closes.
Wayland, macOS, Windows and Flatpak are not supported by this initial backend;
individual applications and popups may have embedding limitations.

App billboards now use HD previews with labels below the content. Flight and
connected app panels include fullscreen controls, so you can use the entire
screen and return to your previous workspace layout. Flight also supports F11;
the app panel keeps a visible exit control while the app owns keyboard input.

### Experimental cockpit workspace

Dockpipe now has a standalone **Cockpit** destination: a pilotable ship with
planets for files, apps, workflows, containers, settings, machines and executions.
Enter app hangars for fullscreen control or open apps in a windshield HUD. Arrange
and resize the HUD and keep that layout between visits. Operational panels reuse
the existing Dockpipe editors and controls, including their workflow Run actions.

Optional controller input and local push-to-talk navigation are included. Native
Linux voice needs the local PocketSphinx English model and audio libraries; no
microphone starts until push-to-talk is held. Native app control remains an
explicit X11 experiment. These capabilities do not replace OS permissions or
provide full platform parity.

Selected files and open apps now raise a holographic preview above their building.
The preview faces the pilot as you move; select again to edit or control the app.
File excerpts are bounded and syntax highlighted. Cockpit planets use 3D geometry
and atmospheric arrival transitions, with middle-mouse look-around inside the ship.
These experimental views retain the existing opt-in app capture and platform limits.

Flying through file and app cities is smoother: the renderer reuses building
geometry and skips structures and faces outside the view. Movement now targets
60 updates per second while idle scenes remain still. Space is black, with soft
colored atmospheric glows around the planets.

Cockpit selection now follows the mouse pointer: click a file or open-app building
to see its camera-facing hologram, then select again to open it. Space and controller
selection still use the crosshair. A visible **Back** button and return portals
provide a way out: folder gates return to the parent directory, while a portal in
the planet sky returns to orbit. Fly through a portal or click its opening or label.
App capture remains opt-in; selecting an app now reveals the control when needed.

Experimental app control now checks that the app actually stays inside its HUD.
If the app closes or returns to the desktop, Dockpipe restores flight and reports
the failure over the preview. Returning from app control also preserves the GPU
setting. Preview support still does not guarantee that an app supports embedding.

Native cockpit buildings now preview before opening, including Containers,
Machines, Executions, Workflows and Settings. Workflow previews show their YAML
without running anything. Settings stays in the cockpit HUD, and embedded apps
have their position and size corrected when they try to restore desktop geometry.
