## Direct-consumption idea assessment

The subsequent user proposal to consume compressed data without full
reconstruction is assessed in the canonical report's “Compiler and framework
consumption of compressed data” section. Distinguish bounded streaming,
operations on encoded values, and demand-decoded native pages. Current whole-JSON
fixture loaders provide a concrete first experiment; compressed native machine
code still requires decoding and the existing full verification/sealing pass.
Direct fixture consumption is now the first compression-for-execution experiment,
with identity work remaining a separate performance track. This addition is
design/source/literature analysis, not implementation or new measured proof.
`direct-consumption-validation.json` in the research evidence root records the
documentation checks; the earlier `final-validation.json` describes its earlier
report postimage and is retained unchanged.

The further hybrid-execution question is addressed in “Hybrid native and compact
execution”: native consumers of encoded data fit the nearer-term framework work;
native and compact-interpreted functions can coexist behind a common Core-derived
contract but require another backend and call/runtime integration. A JIT is
optional. This remains a researched design candidate, with no implementation or
benchmark claim. `hybrid-design-validation.json` records the updated doc checks.

The subsequent request to combine useful improvements is captured in “Combined
roadmap for the foundation goals,” linked from the foundation delivery plan. It
maps verification, encoded-data consumption, compiler representation, storage,
hybrid execution, and recoverability to milestone benefits and a measured adoption
sequence. Performance percentages are not additive; ambitious compression is not
a gate on unrelated language delivery. `portfolio-validation.json` records the
